# 决策：NL2SQL 结果包装层——数据≠答案

状态：implemented

## Problem

NL2SQL 最初把 SQL 结果直接格式化输出。用户飞书实况：「赵敏所在的部门和王强所在的部门，哪个的报销多，多多少」→ 甩两行原始数据让用户自己算。

我尝试用答案层特判修：比较结论特判、聚合别名中文映射、NULL 显示「未录入」、total_sales 前缀匹配……用户当场暴怒：「像这样有一个加一个，加到死都加不完」。

本质：**SQL 查出的「数据」不等于「答案」**，答案层特判是无穷形态。

## Decision

一个机制收编所有形态——结果→回答包装层（`app/service/nlsql.py` 的 `_answer_with_llm`）：

1. 输入：问句 + 真实数据文本（中文列名）+ 确定性衍生信息（两行数值比较时预先算好差值——**算术不让模型算**，防算错）
2. LLM 只做措辞（提示词约束：只能用结果数据、数字/日期写法与结果一致、NULL=未录入、聚合 NULL=无记录）
3. **数字核对兜底**：回答中每个数字必须来自「查询结果+衍生信息+问句本身」，越界回退确定性原文——模型改写数字（2881.30→2881.3）或算错一律拦截
4. LLM 失败回退原文——确定性原文永远是最差可交付底线
5. 多行列表（>2 行）不包装——曾包装层压缩明细时丢部门/姓名列

## Alternatives considered

1. 答案层特判逐形态加规则（被用户否决：加到死加不完）
2. SQL 生成时让模型写比较逻辑（算术错误风险高）
3. 只回原文不包装（「智障」实况根源）

## Consequences

+ 比较/单值/无记录/未录入所有形态一个机制覆盖
+ 数字核对是硬兜底，编造数字物理上不可能
− 每条数据面查询多一次 verify_chat 调用（措辞包装）
− 包装层数字核对只核「数字集合包含」，不核语义正确性（如「A 比 B 多」说反）——残余风险
