# Problem

PDF 摄入在提取文字后仍会对文档内嵌图片统一调用 OCR。普通电子版 PDF 因此产生不必要的 OCR 请求；GLM-OCR 等服务还存在图片大小和页数限制。原实现对整份 PDF 做全局乱码判断，一页乱码也可能丢弃整本文档。Web 与飞书共用 `pipeline.ingest()` 和 `parse.parse_bytes()`，问题会同时影响两条上传链路。

# Decision

在公共 PDF 解析层按页建立文字结果，并按页质量决定 OCR：正常、非空且非乱码的页面只使用文字层，完全跳过图片 OCR；空页或乱码页仅对该页可提取且通过大小门控的内嵌图片调用 OCR。OCR 结果写入同一 `[[page:N]]` 页标记下。pdfplumber 与 pypdf fallback 使用相同的页码、质量闸门和 OCR 上限。移除全局乱码拒绝，单页异常不影响其他页面。

# Alternatives

- 保持全局 OCR：实现简单，但浪费调用并会触发大文档 OCR 限制。
- 所有 PDF 强制 OCR：能处理扫描件，但普通电子文档成本高、速度慢，且现有接口不适合超页数 PDF。
- 引入新的 PDF 光栅化/OCR 依赖：扫描页覆盖更完整，但增加部署依赖；本次先复用已有 PDF 图片对象，后续可单独评估光栅化能力。

# Consequences

普通电子版 PDF 的解析不再被内嵌插图 OCR 阻塞，健康页保留原有页码，混合 PDF 可仅补识别异常页。当前实现依赖 pypdf 暴露的内嵌图片；若扫描页没有可提取的图片对象，仍会返回空内容并需要后续增加页面光栅化方案。Web 与飞书无需改调用方。
