# 决策：文档请求采用统一意图解析与标题归一化

状态：implemented

## Problem

文档生成入口原先由一组宽窄不一的触发正则和独立标题猜测组成。自然问法“帮我这个学习agent的计划书”没有命中触发器，随后被误送到普通知识问答并返回知识库缺口；而继续单独扩大正则又会把“帮我写代码”或“学习计划是什么”误判成文档请求。Web、流式和飞书还存在重复判定入口，标题、用户要点和文档类型可能互相不一致。

## Decision

在 `app/service/docwizard.py` 中采用统一的确定性文档请求解析：

1. 以请求壳/动作词、文档类型后缀和知识咨询负边界组成规则层；计划书、学习计划、学习方案等与通知、报告、方案、纪要、攻略、手册、指南统一处理，具体后缀按专用类型优先匹配。
2. `parse_request()` 一次产出匹配结果、规范化标题、用户要点和文档类型；`matches()`、`guess_title()`、`try_generate()` 委托同一解析语义，不再各自剥前缀或重复猜标题。
3. 标题清理统一空白、控制字符、中英文边界和受控的 `agent` 写法；剥除“帮我/这个”等请求壳，但不把完整原句直接作为云文档标题。目标问法得到《学习 Agent 计划书》；知识问法、查看/修改问法和无文档后缀的“帮我写代码”继续走知识问答或修改路径。
4. 计划书类使用目标、现状、阶段安排、方法和评估调整结构；用户要点同时用于检索 query、生成提示词和事实证据，即使资料无命中也不把文档请求改答成知识库 `NO_ANSWER`。
5. `_route_early()` 继续由流式/非流式共用，并将调用方 user 透传到文档检索；生成结果返回实际来源列表。飞书移除独立的触发词前置判断，统一消费 early route 的 `needs_form`，防止渠道规则漂移。

## Alternatives considered

1. 只为“学习agent计划书”增加一条正则：只能修一个实例，无法覆盖学习计划、项目计划、培训方案等同类自然问法。
2. 让 LLM 进行文档意图分类或标题抽取：确定性可算的路由交给模型会增加成本、延迟和不可重复误判，违反项目路由原则。
3. 继续让飞书和 agent 各自判定：会造成入口行为分叉；统一解析函数可离线测试并由两条 Web 路径共同复用。

## Consequences

+ “帮我这个学习agent的计划书”及同类计划/方案请求进入 DOC_WIZARD，不再被错误记录为知识缺口。
+ 标题、文档类型、用户要点、ACL 检索身份和来源返回口径统一；Web 非流式、流式和飞书共享同一早期路由。
+ 询问、查看、修改和非文档请求有明确负边界，降低短后缀误触发。
− 规则矩阵仍需随新自然问法扩展，标题语言边界（尤其“的”和中英文混写）需要持续回归。
− 文档类型后缀后带明确分隔要点（如“学习 Agent 计划，每天两小时”）现在作为同类请求解析；无分隔的中文尾巴不猜切，需用户使用标点或明确分隔。
− 文档生成仍会调用检索、LLM、事实校验和可能的云文档发布；真实来源和发布链路需在外部环境单独验证。
− 多轮 `revise()` 仍是既有独立回写路径，本决策不宣称它已接入初始生成的统一事实校验链。
