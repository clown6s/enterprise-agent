# 决策：路由去预判——无预闸架构

状态：implemented

## Problem

NL2SQL 数据面接入后，为「省一次模型调用」加了预判正则预闸，判断哪些问法值得试表查询。三轮补丁全部失败：

1. **白名单词表**（_FACT_QUERY）：口语碎片永远补不完——「公司有几位员工」的「几位」、「王强是干什么的」、「赵敏的联系方式」全不在词表，NL2SQL 根本没被尝试，直接兜底「暂无法回答」（用户飞书连测实况）
2. **反转黑名单**（_KNOWLEDGE_QUERY）：黑名单「是什么」误伤「王强是**什么**时候入职的」——标准问法被误判为知识型问法
3. **负向 lookahead 补丁**：用户当场暴怒：「为什么要写死一些去判断？为什么不从知识库里去定义你回答什么，从 skills 中去看你能干什么？」

预判正则的本质错误：用写死词表预测「该走哪层」，而词表永远落后于真实问法。

## Decision

删除全部预判正则。路由链每层按自身定义自判：

- **知识库定义回答什么**：知识问答兜底，检索失败即「暂无法回答」
- **skills 定义能干什么**：SOP 关键词=技能触发注册，制度问法排除（流程/怎么/多少）
- **NL2SQL 自己判断能不能答**：无条件尝试，模型生成 SQL 或空模板（=无法确定→漏回后续层）；提示词规则 4 教模型「提交类/知识类/闲聊输出空模板」

代价：每条非数据问法多一次模型调用（1-3s）——正确架构的代价，用户明确不在乎成本。

## Alternatives considered

1. 继续补词表（打地鼠，被用户否决）
2. 让路正则（_ACTION_QUERY 提交语义让路）——同样是预判，一并删除
3. 路由模型做意图分类——违反「能确定性算出来的事绝不交给模型」且模型路由已验证不可靠

## Consequences

+ 口语变体全覆盖（变体矩阵 290/290 验证）
+ 新数据源/新技能接入零路由改动
− 知识问答类请求多一次 verify_chat 调用（+1-3s 延迟）
− 空结果+金额数字的提交问法仍需「空结果语义修正」兜底（见 nlsql.py 注释）
