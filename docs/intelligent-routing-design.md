# 智能路由与查询架构设计（2026-08-18 深度扫描后成稿，待用户拍板）

## 一、现状盘点（扫描结论）

系统已有五种分发机制，各自为政、互不相通：

| 机制 | 匹配方式 | 执行器 | 数据驱动程度 |
|---|---|---|---|
| 意图规则表 intent/rules.py | 代码正则 | 代码 handler | 无（加业务=写代码） |
| SOP 状态机 plan/sop.py | 代码关键词 | 代码 handlers | 半（sop 表存 keywords+steps_json，但运行时仍用代码 handler） |
| docwizard | 代码触发词 | 代码流程 | 无 |
| route()（闲聊/澄清/知识问答） | 代码正则 | 代码 | 无 |
| KB 知识问答 | 向量+BM25 | LLM+校验链 | 无（兜底层） |

关键发现：
- `skill` 表 schema 早已具备统一注册的雏形（code/name/description/skill_md/
  tool_type/mcp_config/tool_names/status）——**但表是空的，只被当开关用**
- `sop` 表的 steps_json 已描述流程（tool/extract/validate 步骤），但执行仍靠代码
- 路由是「固定顺序分发链」：加一类新功能 = 在 _answer_inner 接一个新分支
- 用户新问法 = 写 handler（意图规则 4 条就是 4 个 handler）

**核心矛盾：能力在代码里，数据在数据库里，两者没打通。**

## 二、目标架构：能力总线 + 查询智能 + 自学习沉淀

### 层 1：统一能力注册表（skill 表真正激活）

每个「能力」一行注册，路由统一遍历：

```
capability:
  code            # 唯一标识
  type            # deterministic（正则直答）/ sql（NL2SQL 查询）/ sop（流程）/ kb（知识问答兜底）/ doc（文档生成）
  matcher         # 匹配配置：regex/keywords（type=deterministic/sop/doc 用）
  executor_ref    # 执行器引用：handler 类名 / sql 模板 / steps_json
  priority        # 遍历顺序（确定性优先于兜底）
  status          # 开关（已有 TTL 生效）
```

- 路由 = 按 priority 遍历能力表 → matcher 命中 → executor 执行 → 统一结果包装
- **加业务 = 后台注册一行**：type=sql 或 sop（steps_json 完整描述）→ 零代码；
  全新能力类型才写一个 handler 类（一次性的类扩展，不是每个问题写代码）
- 现有 5 个工具 + 意图规则 + docwizard 全部收编进表，route() 的闲聊/澄清保留为
  前置层（问候/指代消解不属于"业务能力"）

### 层 2：三级匹配智能（不违背"确定性优先"原则）

- **L1 确定性匹配**：regex/关键词（现有机制，快、准、可解释）
- **L2 语义意图分类**：小模型把问题分到能力候选集（n-way 分类 + 置信度）——
  模型只**缩小候选集**，不直接执行；置信度低 → 追问澄清或落 KB 兜底。
  模型路由不可靠的教训仍成立：模型提供建议，执行永远过确定性校验
- **L3 审计可解释**：每次分发记录"命中哪个能力、匹配依据、置信度"——
  走错路可追溯可修正（修正 = 改配置行，不是改代码）

### 层 3：查询智能（NL2SQL + 多跳编排）

**3a. schema 注册表**（模型可见的数据面由登记决定）：
- 每张表登记：表名、用途说明、列清单（中文含义+示例值）
- 未注册的表/列对模型不可见——sys_user.password_hash 这类永远不进注册表

**3b. NL2SQL（单表/单源查询）**：
- 问句 → 模型生成 `{sql_template, params}`（字面值走占位，不拼字符串）
- 确定性校验器五关，不过即拒绝执行：
  1. SELECT-only（写关键字出现即拒）
  2. 表名在注册白名单内
  3. 列名在注册列内
  4. 单语句（分号注入拦截）
  5. 行数上限（LIMIT 强制，防全表灌爆）
- 参数化执行 → 结果行确定性格式化（数字来自真实行，零编造空间）

**3c. 多跳编排（跨表/跨源复合问题）**：
- 复杂问题（"李娜报销了多少，她什么职位，公司报销政策是什么"）→
  模型建议拆解为子问题列表 → 每个子问题**递归走能力总线**（可能命中
  NL2SQL、意图规则、KB 任一）→ 确定性合并为单一答案
- 拆解是模型建议、每步执行仍被各自守卫管住（SQL 校验器/术语核对/闸门）
- 合并层每片带来源（表行/文档 chunk），拼装逻辑是代码不是模型——
  与跨文档拼接防线同原则

### 层 4：知识层（现状保留，注册为兜底能力）

KB 检索+生成+校验链+图谱兜底+闸门——已足够强，作为最低优先级能力注册进
总线。NL2SQL 失败/校验不过 → 落 KB 兜底。

### 层 5：自学习沉淀（系统越用越强）

1. **采纳升级**：👍 采纳通过的问答 → adopted_qa 表 → 下次相同/近似问法
   确定性直答（秒回零 LLM），👎 到阈值降级回慢路径
2. **SQL 模式沉淀**：NL2SQL 成功执行的查询 → 沉淀为高频查询配置，
   后续命中走直配（从"生成"降为"直查"）
3. 词汇对齐/缺口聚类的自学习闭环已有，同形态扩展

## 三、落地顺序建议

1. **打地基**：员工目录统一到 MySQL employee 表（种子=现有 8 人，加
   mobile 字段，请假 SOP/意图问答/飞书身份全查同一张表）
2. **能力总线**：skill 表激活 + 路由改造（现有 5 工具收编，type 字段驱动）
3. **NL2SQL**：schema 注册表 + 校验器 + 执行器（表查询零代码化）
4. **多跳编排**：拆解-分派-合并
5. **采纳升级**：adopted_qa 直答层

每步独立可验收，回归棘轮全程护航。

## 四、与既有原则的关系

- "能确定性算出来的不交给模型"：不变——模型从路由**决策者**降为**建议者**，
  执行永远过确定性校验
- "无依据内容不出门"：不变——NL2SQL 答案数字来自真实行；多跳合并每片带来源
- "改类不改实例"：本设计就是类级形态——能力/表/查询全部注册表驱动
- 安全：SQL 校验器 = expr 注入白名单模式的同款升级（表/列/语句三层白名单）
