# 事故复盘（postmortem）0002：审批指令正则截断 hex 后缀

状态：已解决

## 摘要

飞书/对话审批入口「同意/拒绝 <单号>」从上线起从未工作过。根因：`_COMMAND` 正则
`[A-Z]+\d{8,}` 遇到 apply_no 的 hex 后缀字母（如 `LEAVE2026082042DFC925` 中的 `DFC925`）
就停止匹配，只截到 `LEAVE2026082042`，丢掉 hex 后缀 → 永远匹配不到真实单号 →
返回"未找到"。补覆盖率时 test_approval.py 浮现。

## 影响

飞书审批人回复「同意 LEAVE2026082042DFC925」→ 系统「未找到您名下的待审批单」
→ 审批闭环自建功能对外不可用。因回归无此路径用例，上线后未被发现。

## 时间线

- 2026-08-19：审批闭环自建，`try_approval_command` + `_COMMAND` 正则上线。
- 至 2026-08-20：用户从未报告审批指令失败（可能未使用此入口，或以为单号不对）。
- 2026-08-20 补覆盖率时写 `test_approval.py`，用真实格式 apply_no 测试 →
  正则只截到前半段 → 全部 4 条 `try_approval_command` 用例失败。
- 修复：`[A-Z]+\d{8,}` → `[A-Z]+\d{8}[0-9A-Z]*`（精确匹配 8 位日期 + 吃 hex 后缀）。

## 根因

1. **apply_no 格式设计未考虑正则匹配**：单号 = 前缀(大写字母) + 8位日期 + 8位hex
   (含 A-F 字母)。正则 `[A-Z]+\d{8,}` 的 `\d{8,}` 遇到 hex 字母就停——这是格式
   设计和正则设计的隐含冲突，不是"忘了哪个字符"。
2. **回归用例不覆盖审批指令路径**：29 条回归测的是 SOP 提交（`帮我请假` → 确认 →
   提交），不测审批人回复「同意 <单号>」——审批入口是独立路径，没有用例。
3. **正则靠肉眼写不靠测试验证**：正则写完没有用真实单号跑一遍，靠"看起来对"。

## 已添加的防护措施

1. **正则修复**（`app/plan/approval.py`）：`[A-Z]+\d{8}[0-9A-Z]*`，附根因注释。
2. **test_approval.py 新增 4 条**（`try_approval_command` 路径）：命中/未命中/非指令/无单，
   用真实格式 apply_no（`TESTCOV2026082000000001`，含 8 位日期）。
3. **补覆盖率时发现**：不是用户实况触发，是 test_approval.py 主动浮现——
   证明"补覆盖率"本身有独立价值（dsh 三-11"回归测试必须证明有效"的实证）。

## 教训

1. **单号格式设计要考虑下游正则匹配**——hex 后缀含字母会和 `[A-Z]+\d+` 类正则冲突。
2. **独立路径必须有独立用例**——SOP 提交路径测了不等于审批指令路径也测了。
3. **正则写完用真实数据跑一遍**——靠肉眼写正则等于没测。
